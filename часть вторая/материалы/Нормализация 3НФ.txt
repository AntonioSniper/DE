Нормализация логической модели — 3НФ

В обоих файлах по восемь листов: roles, event_types, events, statuses, users, applications, application_members, reviews. Имя листа совпадает с именем таблицы SQL и CSV-файла.
В логической модели описаны поля; в импортных листах первая строка — только имена этих полей в том же порядке, остальные строки — записи. Метаданные PK/FK, типы и пояснения в CSV не помещаются: ограничения задаются схемой SQL.

1НФ: в ячейках отдельные скалярные значения. Участники команды вынесены в application_members: один участник — одна строка. ФИО — единое строковое поле по ТЗ, не список людей. Пустые импортные листы содержат заголовки, а не выдуманные записи.
2НФ: каждый объявленный потенциальный ключ одноатрибутный. Частичной зависимости от части составного ключа нет.
3НФ: при зависимостях предметной области неключевые поля не определяют другие неключевые поля. Ключи и типы указаны в заголовках листов; функциональные зависимости перечислены ниже.

roles: role_id → role_name.
event_types: type_id → type_name.
events: event_id → event_name, type_id. Название типа не дублируется, берётся из event_types.
statuses: status_id → status_name.
users: user_id → остальные поля; login → остальные поля. login уникален. Название роли не хранится в users.
applications: application_id → user_id, event_id, event_date, contact_phone, contact_email, status_id. Название, тип события, название статуса и профиль пользователя здесь не дублируются.
application_members: member_id → application_id, full_name. Наличие одинаковых ФИО у разных людей допустимо; ФИО не считается уникальным ключом.
reviews: review_id → application_id, review_text; application_id → review_id, review_text. UNIQUE(application_id) обеспечивает не более одного отзыва на заявку. Отдельные user_id и event_id в reviews не нужны — определяются через заявку.

Допущения предметной области: дата и контакты представителя относятся к конкретной заявке. События из каталога не имеют фиксированных дат в ТЗ; одна и та же позиция каталога может выбираться с разными датами. Контакты команды могут отличаться от профиля подавшего заявку, поэтому не выводятся из user_id. Телефон, email и ФИО не объявляются уникальными и не определяют друг друга. 3НФ оценивается по этим зависимостям и ограничениям схемы, а не по совпадениям в примерах данных.

Порядок импорта: roles → event_types → events → statuses → users → applications → application_members → reviews.
Кодировка UTF-8, разделитель запятая, первая строка — заголовки. SQL остаётся источником PK, FK, UNIQUE и типов данных.
